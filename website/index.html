Agent-engineering capstone · Vizuara AI Labs

Build a support agent that answers, and hands off before it guesses.

In this capstone you build a customer-support agent that answers from a real knowledge base and a ticketing system, runs a guardrail on every step, and escalates to a human when its answer is not well supported. You finish by running the eval harness on your own held-out tickets and reporting the numbers it measured.

What you'll build

One agent you can put in front of real users.

You build a customer-support agent with tool use over a knowledge base and a ticketing system. It reasons with Claude Opus 4.8 (claude-opus-4-8), retrieves answers that cite their source, runs a guardrail stack on every step, and decides whether to answer or escalate based on how well its draft is supported.

The point of the project is reliability, not a demo. A support agent is only useful if it is right most of the time and says so when it is not. So the single graded artifact is the eval report the harness writes when you run it on your own held-out tickets: eval_report.json. That file carries the resolution rate, the hallucination rate, the tone score, and the handoff threshold you measured. Until you run the harness, none of those numbers exists, and you do not report one.

By the end you can say the project back in one sentence: an agent that answers grounded questions with citations, escalates the rest, and proves its reliability with numbers you measured. Here are the components you build:

  • An agent loop with tool use over the knowledge base and the ticketing system. Tool input is parsed as JSON, not string-matched, so a tool call means exactly what it says.
  • A knowledge base that cites its sources. Documents are chunked, embedded (text-embedding-3-large by default, or a local bge-m3), and stored in pgvector with an HNSW index. The agent may cite only chunks it actually retrieved.
  • A guardrail stack: PII redaction with Presidio, safety and refusal with Llama Guard 4, and an injection quarantine that defangs instructions hidden inside tool output.
  • Confidence-based handoff. A per-turn score of how well the answer is supported by its sources, and the decision to escalate below the threshold τ*.
  • Tracing and cost accounting. OpenTelemetry GenAI spans for every step, and a per-call dollar cost computed from the real usage fields, exported to Langfuse.
  • An offline eval suite that measures resolution rate, hallucination rate, tone, and the τ* that holds hallucination under target.
Why it matters

A demo answers one question. A deployment answers thousands.

The cost of a confident wrong answer in production is a refunded order or a lost customer, so the target here is reliability, not a clever transcript. The hard part is consistency: even a state-of-the-art function-calling agent (GPT-4o) succeeds on under 50% of τ-bench tasks at pass^1, and stays under 25% at pass^8 in retail. Being right once is easy; being right every time is the problem.

Two levers make the agent safe to deploy, and you build both. The first is the guardrail stack that runs on every step. The second is the confidence threshold τ*, which hands the ticket to a human before the agent guesses. An agent that escalates when the support is thin is doing its job, not failing at it.

How to finish this capstone

You are done when the harness has measured it.

The deliverable is a working agent plus the eval report it produces on a held-out ticket set. The single graded artifact is eval_report.json (with its companion eval_report.md), written by make eval on a real run.

The target to hit

The headline for this agent is the resolution rate and the hallucination rate on your held-out set, together with the τ* that holds hallucination under target. The target used in the threshold sweep is a hallucination rate at or below 2% (--hallucination-target 0.02). That is a bar you choose, not a score you claim; you report the τ* that meets it and the resolution coverage you keep at that cutoff.

The honesty rule

Every number you report is one you measured with the harness. A cited reference keeps its source URL and describes another system, not your agent. A quantity you measure is written as a metric name and its command until a run fills it in. Nothing is fabricated, and a cited figure is never presented as your agent's score.

  • make test passes: the guardrails, the retrieval-to-citation path, the confidence gate, and the loop all hold without an API key or a GPU.
  • make eval has run on your held-out set and written eval_report.json with a measured resolution rate and hallucination rate.
  • The threshold sweep has picked a τ* that holds the hallucination rate at or below your target, and HANDOFF_THRESHOLD is set to it.
  • Every number you report came from a run. Cited references still carry their source URL, and no "you will measure" cell is filled in without a run behind it.
Reproduce

The commands are real. The numbers they print are yours.

Nothing below hardcodes a key. The eval and threshold commands call the live model on real hardware; they exit early with an instruction if ANTHROPIC_API_KEY is unset, rather than printing a number. The unit tests run with a fake model client and a deterministic embedder, so they need neither a key nor a GPU.

Laptop path · no API key, no GPU
# install and configure $ make install $ cp .env.example .env # fill in ANTHROPIC_API_KEY and the rest # deterministic guardrail + loop tests — fake client, deterministic embedder $ make test
Full path · live model + the guardrail GPU
# stack: Postgres+pgvector, Llama Guard 4, OTel collector, Langfuse $ make db-up # ingest the sample knowledge base into pgvector $ make ingest # run the service — POST /chat, GET /healthz $ make serve # offline eval over the held-out ticket set $ make eval $ python -m eval.run --suite heldout --check hallucination $ python -m eval.run --suite heldout --check tone # pick the handoff threshold that holds hallucination under target $ python -m eval.threshold --hallucination-target 0.02 --k 8 # optional external cross-check against tau-bench $ python -m eval.tau_bench_adapter --domain retail
Cost is arithmetic, not a benchmark

Every call's cost is usage.input_tokens, usage.output_tokens, and the cache fields multiplied by the published rates. POST /chat returns cost_usd for the turn, and each span carries its token counts and cost. The tracing layer reports the dollar cost of a run exactly, because it is arithmetic on the real usage fields the API returns, not an estimate.

What to watch out for

Where the repo stops and your data begins.

  • It ships no agent score. Resolution rate, hallucination rate, tone, and τ* are commands you run on your own held-out set and your own hardware, not values shipped in the repo.
  • The cited figures are other systems. The τ-bench and AgentDojo numbers describe GPT-4o and similar agents. They set a rough ceiling for the problem and are never your agent's result.
  • The sample data is scaffolding. The tickets and KB in eval/datasets exist to wire the pipeline. A real resolution number needs your own labeled tickets and your own corpus.
  • Confidence alone is not a promise. The confidence score bounds hallucination only together with a measured τ*. Without the threshold sweep it is just a number.
  • Treat tool output as untrusted. A knowledge-base article or an order record can carry an instruction aimed at the agent. The injection quarantine hands it to the model as annotated data, so it is summarised, not obeyed. The test in tests/test_injection.py asserts this, mirroring the AgentDojo reference where an indirect-injection attack reaches up to 53.1% success against an undefended agent.
  • Keys and prices drift. Model IDs are the exact strings the code uses; never append date suffixes to the Opus, Sonnet, or Haiku aliases. Prices are the strings cached 2026-06-24; confirm against the live pricing page before a launch.
