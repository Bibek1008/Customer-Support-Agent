# Render Native Python deployment

The repository blueprint is `render.yaml`. It defines one native Python web service, pins Python to 3.12 via `.python-version`, installs spaCy's small English model during the build, and configures Presidio to use it explicitly. Startup checks that the model is installed before initializing Presidio, so it never downloads or installs a model at runtime. It uses a bounded single-worker runtime and `/healthz`, and configures PostgreSQL persistence, Groq generation and safety, FastEmbed `BAAI/bge-small-en-v1.5` at 384 dimensions, and Langfuse tracing tagged as `production`. Answers use the verified extractive mode.

Before creating or updating a Render service, configure `DATABASE_URL`, the final HTTPS `APP_ORIGIN`, `GROQ_API_KEY`, distinct random `ADMIN_API_KEY` and `SERVICE_API_KEY` values of at least 32 characters, and `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, and `LANGFUSE_BASE_URL` in Render's environment settings. The blueprint marks these as secret/manual values. Do not put credentials in `render.yaml`, source files, or browser code.

The service expects the support schema and approved policy chunks to exist in PostgreSQL. Database setup and knowledge-base ingestion are separate write operations. Do not run migrations or ingest into Neon until the database target and operation have explicit approval. The current Neon inventory already contains all five active office-store policy sources embedded with FastEmbed BGE Small at 384 dimensions, so re-ingestion is not currently required. If a future source or embedding change requires ingestion, first take a verified database backup, prepare the new chunks locally, and validate counts, metadata, dimensions, and citations before an explicitly approved additive upsert. Never use `--reset` on a shared database.

Render checks `/healthz` for process liveness. This endpoint intentionally does no database, knowledge-base, Presidio, or provider work, so it can answer while those checks run. `/readyz` reports production readiness and returns HTTP 503 until PostgreSQL schema, compatible approved policy chunks, and Presidio are available. Customer and staff operations that require persistence also return a controlled 503 until readiness succeeds. Database and policy metadata are checked with one SQL round trip; startup does not initialize the vector store, download a model, or generate embeddings.

Production startup validates configuration and credentials synchronously, then schedules Presidio and PostgreSQL/policy readiness checks in a background thread after the HTTP lifespan begins. Startup does not make a Groq safety request. Safety classification remains mandatory for every customer input and generated assistant response; an unavailable or invalid verdict returns HTTP 503 and fails closed. This keeps provider latency out of startup without weakening request guardrails. Logs report each startup operation and elapsed milliseconds; they include operation names and status only, never keys, prompts, or customer data. Optional tracing initialization is lazy on first use.

The Render logs provided for the previous timeout did not include per-operation timings, so they cannot identify which operation consumed that deployment's startup window. Source inspection confirmed that startup synchronously issued a live Groq safety inference with a network timeout, in addition to sequential database, knowledge-base, and Presidio checks. The live inference was removed from startup; the added timing logs will identify any future slow readiness operation directly.

## Local memory and lifecycle measurement

A Windows Python 3.12 probe measured the production FastAPI lifespan with the database readiness check and hosted safety classifier mocked, Presidio using `en_core_web_sm`, FastEmbed BGE Small loaded and queried, a psycopg pool configured for one to two connections, and 24 concurrent mocked `/chat` requests. Peak process working set was **375.9 MiB** and peak private committed memory was **709.1 MiB**. Presidio initialization took **1.94 s**, FastEmbed's first local query took **0.79 s**, and FastAPI lifespan shutdown took under **1 ms**. The dummy pool used a refused loopback address, not PostgreSQL or Neon; its close took **1.62 s** while its connection attempt timed out. No hosted inference or trace export was run for this measurement.

These are local Windows process measurements, not Render cgroup measurements. The working set is below the Free plan's nominal 512 MiB limit in this run, but this does not prove the Render deployment will stay below it; verify Render's memory chart after deployment. The private committed-memory figure is not directly comparable to Render's physical memory usage.

After the startup change, a Windows Python 3.12 production-lifespan probe used valid placeholder credentials, the real installed Presidio `en_core_web_sm`, and a mocked database readiness check. No safety inference, database connection, FastEmbed model load, or embedding generation ran. Lifespan setup returned in **20.1 ms**; Render's `/healthz` returned 200 immediately. Background Presidio initialization took **2,159.6 ms**, and the mocked database/policy check took **under 1 ms**. At readiness, process working set was **193.2 MiB** (peak **202.6 MiB**) and private committed memory was **525.3 MiB**. These are local Windows measurements, not Render cgroup measurements; production database latency and first-request FastEmbed memory are not represented.
